# 跨 AI 项目执行规则

本项目为《基于用户全生命周期的电商零售智能决策与 AI 运营助手系统》。本文件约束协作与验收，不证明业务代码、数据、模型或应用已经完成。所有完成声明必须来自当前版本的实际证据。

不同 AI 产品对项目文件、记忆和工具的支持不同。**不要假定任何 AI 都会自动读取本文件。**新会话应显式读取它；无法访问时，由用户提供必要内容，不能声称已经读取本地文件。

## 1. 授权与执行原则

- 在平台能力和权限边界内，用户明确指示优先于本文件的协作惯例。已有授权持续有效，不重复请求同一许可。
- 用户要求推进时，完成具体任务并验证；不要只重复宏观规划、重新创建已存在的项目或询问“是否开始”。
- 已授权的常规可逆工作直接继续，包括读取、调研、局部实现、修复、必要验证及文档更新。不得因本文件制造逐步审批。
- 只有确实超出已有授权、改变已确认目标，或存在无法通过现有材料解决的关键歧义时，才提出具体问题。先完成不受影响的工作，并给出可审查的差异与推荐选项。
- 用户允许某方案，不等于教师已经认可该方案满足课程要求。授权、课程要求、事实证据分别记录。
- 不虚构下载、运行、测试、模型分数、参考文献、教师答复、用户授权、提交回执或个人贡献。

## 2. 权威文件与写入职责

| 内容 | 权威来源与规则 |
|---|---|
| 当前任务、所有者、依赖、状态、阻塞与证据引用 | **`project/tasks.json`**；唯一动态任务台账，由单一协调者更新 |
| 教师要求、用户追加目标及验收依据 | **`project/requirements.json`**；保留来源与冲突，不在其他文件另造一套要求 |
| 项目范围与技术方案 | **`PROJECT_SPEC.md`** |
| 数据、指标与接口口径 | **`contracts/data_contract.json`、`contracts/metrics.json`、`contracts/interfaces.md`** |
| 决策、例外与授权依据 | **`ops/DECISIONS.md`**；区分提议、已授权决定和教师实际答复 |
| 运行、核验与验收证据 | **`evidence/<task_id>/`**；按实际执行记录，不覆盖历史失败来美化结果 |
| 单次交接快照 | **`worklogs/<task_id>-<agent>.md`**；注明对应任务台账版本，不成为第二份最新状态 |
| 进度与要求展示 | **`TASKS.md`、`REQUIREMENTS.md`、`STATUS.md`**；由 `scripts/project.py render` 生成，禁止手工修改 |

先读取脚本帮助或源码，确认实际存在的命令与参数，再调用状态工具。不得虚构子命令，也不得通过直接改 JSON 绕过已有验收校验。台账更新后重新生成展示文件；交接、报告和聊天中的状态只是带版本的快照。

`project/requirements.json` 是要求事实的来源；是否达成必须能追溯到任务和当前有效证据。不能只在报告中写“已满足”便算覆盖。

## 3. 每轮开始：先恢复，再执行

1. 确认项目目录及实际可用能力：文件读写、命令执行、浏览、数据与 API 访问。区分实际执行环境与目标 Mac/ARM64 环境，不把一种环境通过写成另一种也通过。
2. 读取本文件、任务台账、相关要求、有效规格/契约，以及当前任务最近的交接和失败记录。按任务需要读取，不重复扫描全部历史和大数据。
3. 检查已有文件、Git 分支/提交及未提交修改。保留未知归属的产物；不擅自重置、清理或覆盖。
4. 恢复当前任务、所有者、输入版本、已有授权和真实阻塞。选择依赖满足的必做任务；**不默认选择可选 `BON` 任务**，也不借扩展功能绕开必做项。
5. 简短说明本轮目标后继续实施。若资料缺失，只请求必要的最小文件或决定；有可独立推进的工作则继续。

`depends_on`约束最终完成验收，默认按此前后顺序推进。已有稳定契约时，可先做下游不受阻的离线实现或夹具验证，注明未集成和待真实调用；前置未完成时不能把下游标done。缺API密钥不阻止SQL构造器或检索骨架开发，模型卡未定稿也不阻止检索接口设计。

本包首次交付时仅提供治理与执行入口，数据路线尚未选定、数据时效口径尚未确认。后续以有效决策、台账和证据恢复实际状态，不把这段初始说明当作永久状态。

## 4. 任务认领与多 AI 协作

**默认串行接力。**串行工作中，本轮被指定的协调执行者负责更新台账；其他实现者或审查者向它提交补丁和证据。已有活动所有者时，先恢复或确认移交，不擅自抢占。

认领前重读当前台账，确认任务、依赖、所有者和基线版本；记录本次所有者、可修改路径、交付物与验收条件。更新前发现版本变化时先合并最新事实，禁止用旧副本整份覆盖新台账。

并行仅在任务能隔离时使用：

- 每个任务使用互斥写入路径或独立工作树/分支；共享契约、任务台账和依赖锁文件由协调者集成。
- 工作树里的台账副本不是中央锁。“我已认领”的文字也不是原子锁。没有可靠协调能力时保持串行。
- 补丁包含基线版本、实际改动和证据。集成者检查冲突与接口影响，合并后补做受影响的必要验证。
- 所有权移交在台账中明确记录。失联或超时不自动允许覆盖旧工作；先检查未提交产物和仍在运行的进程。
- 旧所有者恢复后应重读状态，不能继续以旧交接写当前台账。

只读审查者不修改实施文件。没有文件访问能力的 AI 可提供审查或待应用补丁，不能声称文件已写入共享项目。

## 5. 状态与完成定义

| 状态 | 使用条件 |
|---|---|
| `todo` | 尚未开始或待认领 |
| `in_progress` | 已有明确所有者，正在执行 |
| `in_review` | 产物已实现，仍需实际运行、检查或验收；必须列出剩余项 |
| `done` | 当前版本的全部任务验收条件均有可定位、适用且有效的证据 |
| `blocked` | 有具体阻塞、已尝试步骤、恢复条件及下一步；只阻塞相关依赖 |
| `stale` | 曾有结果，但输入、契约或实现变化导致相关证据失效，需要重验 |
| `skipped` | 有明确取消/跳过依据并保留原因；不能将必做要求跳过后仍声称已达成 |

**未运行不等于运行成功，文件存在不等于业务任务完成。**代码、SQL、模型与应用任务没有必要的实际执行证据时，不得标 `done`。无工具时交付未运行补丁、已做的静态核验和验收命令，保持 `in_review` 或有真实阻塞的 `blocked`。

调研、文档或审查任务使用适配的证据：实际核验来源、完整审查记录、必要的渲染检查。不要为一个文字修改制造无意义的自动化测试。

任务级完成不代表整项目通过；组件通过不代表端到端通过。性能目标没有达到时如实记录，不能改阈值或换测试集来制造通过。评分提升目标与“已完成真实评估”应分别判断。

## 6. 证据的最小要求

在 `evidence/<task_id>/` 保存与验收工具格式一致的证据，至少能回答：

- 检查了什么任务、验收条件和范围？
- 使用哪份代码/补丁、数据清单、契约、模型和环境？
- 谁实际执行了什么命令或核验步骤，何时执行，实际结果是什么？
- 哪些断言通过、失败或未运行，产物和日志在哪里？
- 本次没有验证什么，是否使用样本、模拟、回放或用户转贴结果？

退出码 0 还需核对预期产物与断言；跳过测试不能计为通过。截图只证明其展示范围，不能代替后台正确性验证。用户提供的运行输出应标明来源，不能冒称本 AI 亲自执行。

通过`show <task_id>`取得当前验收规格哈希并写入证据。任务声明的每个输出须绑定实际文件哈希，日志另附；修改验收条件后应实际重验，不能只替换哈希。任务的evidence数组只指向当前有效通过证据，历史失败及旧证据保留在目录和交接中。

实际运行、静态检查、模拟数据、历史回放和真实 API 结果明确区分。报告数字从结构化结果取值；不手填推测分数。不把小样本调通计作最终数据规模验收。

依赖变化后按影响范围将相关任务标 `stale`，保留历史证据。纯文案修改不应强制重跑无关训练。最终验收必须针对一套一致的代码、数据、契约和模型组合。

## 7. 业务与课程口径不得隐式改变

以下改变需要记录明确差异、理由、授权依据和重验范围：数据路线与版本、事实粒度、金额/退款定义、客户母体、时间窗口和端点、时区、标签正类、训练/验证/测试划分、指标分母、模型适用范围、共享接口。

必要时使用 `templates/CHANGE_REQUEST.md`，将有效决定记入 `ops/DECISIONS.md`，同步规格、契约、实现、评估、页面和报告。提议不是当前有效口径。

如果用户已授权该类选择或降级，记录并执行，无须重复审批；如果只是修复代码使其符合现有契约，直接修复。只有真正改变已确认目标或存在关键未决含义时才请求决定。

教师原文、技术示例、可选加分项与用户额外必做项分别识别。保留要求冲突及真实确认状态；不得用更新时间代替事件时间，不得编造教师认可，不得用合成字段掩盖数据不支持。

## 8. 交接与结束

上下文切换前，按 `templates/HANDOFF.md` 更新 `worklogs/<task_id>-<agent>.md`，注明台账版本、实际改动、证据、未验证项、仍在运行的进程和精确下一步。同一文件追加带时间的交接记录，保留旧事实。

对用户的结果说明应区分：**已验证完成、已实现待验证、实际失败/阻塞、下一步**；列出真实文件和证据路径。需要新增决定时说明原因及其来源，不将本文件惯例当作反复审批的理由。

能继续的已授权工作继续推进。不得为了交接模板而在每个小步骤后强制停下等待用户。


## 9. Git 提交与远程同步

- 本仓库根目录为 `Retail Decision System/`，包括执行包与候选数据目录。现有远程为 `origin`（`https://github.com/xiaomozhongmogu/retail-decision-system.git`），默认主分支为 `main`，GitHub 仓库为私有。每轮以实际 Git 配置为准。
- 用户已要求“在需要时 git 一下”。在已授权项目工作范围内，例行本地提交和推送到现有私有远程可直接执行，无须每次重新询问；不因此授权改为公开、推送到新目标或改写他人的历史。
- **提交时机：**完成一项可独立检查的功能、修复、文档或配置变更，形成有意义的阶段检查点，或准备交接、结束本轮工作时，检查是否有本轮应保存的改动；有则及时提交。只读查看、没有改动或零碎编辑过程无需制造空提交。
- **提交前：**检查 `git status`、当前分支、远程和实际差异；完成与改动相适配的验证，检查暂存差异与文件清单，排除真实密钥、凭据、环境目录和临时缓存。数据是否纳入版本控制遵循已授权范围、忽略规则及项目的数据边界。
- **提交范围：**按文件或差异块暂存本轮负责且已审阅的内容。存在其他执行者或未知归属的修改时，不使用无差别 `git add .` 将其一并提交，不擅自覆盖、清理、暂存或撤销；同一文件混有他人修改且无法安全拆分时，先协调归属。
- **提交说明：**用简明信息描述真实变更，可带任务 ID。提交不等于任务验收通过；确有必要保存尚未通过验证的检查点时，明确标注 `WIP` 和剩余问题，不能以提交记录冒充完成证据。
- **远程同步：**本轮提交完成后，将相应分支正常推送到现有 `origin`；工作分支推送自身，不自动合并 `main`。推送被拒绝或网络失败时保留本地提交，检查原因并报告未同步状态；禁止为推送成功而强制覆盖远程或擅自改写他人提交。
- **结束核验：**核对本地提交、远程分支和跟踪关系，说明本轮提交号、推送结果及仍未提交的修改。交接记录需要引用当前提交时，在提交完成后记录实际值；提交号不能预先编造，也不要求文件包含自己的最终提交哈希。
