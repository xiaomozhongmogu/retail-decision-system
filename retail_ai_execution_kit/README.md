# 电商零售智能决策：跨 AI 项目执行包

这是一个长期推进项目的执行基线，包含 **49 项要求映射、92 个任务（85 核心＋7 可选）、验收规则、初始化提示词及协作协议**。它不是已完成的业务系统。当前正式主数据未确定，业务任务初始验收数为0；已有调研和本包材料可以核验后复用。

## 1. 第一次使用

1. 将完整包解压到一个新项目目录。已有仓库时先比较并合并缺失文件，不覆盖已有台账、代码、契约或未提交修改。
2. 阅读`STATUS.md`看真实状态，阅读`TASKS.md`选择工作，`REQUIREMENTS.md`查看老师要求对应到哪里。
3. 让一个AI承担本轮协调执行，实际访问项目目录，将`INIT_PROMPT.md`中的提示词发给它。
4. 先盘点现有成果和环境，按依赖推进。课程数据时效未解决时做候选核验、接口和工程准备，不假称数据已合规。
5. 每项实际完成后保存证据，由协调者更新`project/tasks.json`并重新生成展示文件。

不同AI不自动共享记忆，文件名也不保证被自动读取。**一个共享项目目录/仓库、一个权威台账、一套有效契约**是接力基础。

## 2. 各文件的用途

| 文件 | 用途 | 是否直接编辑 |
| --- | --- | --- |
| `AGENTS.md` | 长期协作、权限、事实与验收规则 | 有明确变更理由时修改 |
| `INIT_PROMPT.md` | 每个新AI会话的启动入口 | 通常复制使用 |
| `PROJECT_SPEC.md` | 项目范围、技术路线和语义基线 | 变更须同步契约及影响任务 |
| `project/requirements.json` | 原文要求、用户承诺、质量目标、可选项 | 需求维护者修改 |
| `project/tasks.json` | 唯一当前状态：任务、依赖、owner、证据 | 仅协调者修改 |
| `TASKS.md` / `STATUS.md` / `REQUIREMENTS.md` | 可阅读任务、当前状态和追溯矩阵 | **自动生成，不手改** |
| `ACCEPTANCE.md` | 跨模块验收矩阵与阶段关卡 | 规则变化须留理由 |
| `contracts/` | 数据、指标和公共接口 | 指定负责人统一维护 |
| `ops/DECISIONS.md` | 真实决定、待确认项、教师解释 | 保留来源及历史 |
| `ops/TEAM.md` | 真实学生分工和贡献 | 团队按实际填写 |
| `templates/` | 派单、交接、变更、证据、实验与报告模板 | 复制到相应工作位置使用 |
| `sources/` | 三份原始课程附件、提取文本、哈希 | 原件不改；按教学范围使用 |
| `docs/reference_registry.md` | 14篇文献种子，正式引用还需按主张核验 | 维护阅读层次和引用证据 |
| `evidence/` / `worklogs/` | 实际验收证据／每次交接历史 | 按任务分别保存 |
| `scripts/project.py` | 结构、依赖、证据及阶段状态检查 | 不为制造通过而改校验 |

## 3. 已可运行的治理命令

只需Python标准库。在项目根目录：

```bash
python3 scripts/project.py validate
python3 scripts/project.py next
python3 scripts/project.py show DATA-02
python3 scripts/project.py render
python3 scripts/project.py gate proposal-ready
```

- `validate`返回0只说明台账及已声明证据符合结构规则，不说明系统已完成。
- `gate`初始返回2并列未完成任务，是正确的阻断结果。
- `render`只生成三个展示文件，不自动修改任务状态。
- `show <任务ID>`只展开该任务、相关要求和验收规格哈希；新AI不必每轮完整复制92项任务。
- 脚本不执行台账内的命令字符串，不自动运行ETL/训练，也不会替你联系教师或提交材料。
- 治理工具自测：`python3 scripts/test_project_tool.py`。测试夹具不是项目业务证据。

业务命令仍待实现，见`docs/COMMANDS.md`。本包不包含已训练模型或可启动的Streamlit业务应用。

## 4. 每轮怎么交给AI

### 同一工作目录的AI

发送INIT_PROMPT，再加一句：`本轮完成DATA-02；以当前台账为准，保留已有修改，完成后实际核验并交接。`

### 不同平台的AI

上传**最新**的AGENTS、项目规格、任务/需求JSON、相关契约、决策和该任务必要的源码/数据样本/证据。它不能访问目录时，要求提供待应用补丁和未运行说明；集成者实际应用并验证。
不要把全部原始数据无差别上传，也不要用最初下载的包覆盖已经推进的仓库。

### 多个AI同时工作

默认串行最容易管理。确需并行，指定一个协调者管理台账和公共契约；其他AI只写互斥目录或独立工作树，返回补丁和证据。AGENTS文件不是进程锁，工作树内的任务副本也不是中央锁。
不可隔离的共享文件串行修改；失联代理恢复时先读最新状态，不能继续覆盖。

任务依赖约束最终验收。没有API密钥或模型卡未定稿时，仍可基于稳定契约先做SQL构造器、检索接口和夹具测试；保持未集成/待验证，不提前done。正式研究数据的“全量”是已冻结研究范围，不是发布者所有无关文件。

## 5. 如何登记完成

1. 将任务设为`in_progress`，填写owner及实际基线；不能抢占已有活动owner。
2. 按任务输出实现，执行验收或适配的文档/来源审阅。
3. 在`evidence/<task_id>/`写JSON证据，示例结构见`templates/EVIDENCE.json`。从`show`取得当前`task_spec_sha256`，把证据绑定到本次验收规格。`inputs`与`artifacts`写实际存在文件和SHA256；任务声明的每个输出都必须在artifacts中有实际哈希，日志可以另外附加。不要引用动态台账自身形成循环哈希。
4. `acceptance_results`按任务验收条件从1编号，逐条填真实finding和passed/failed/not_run等结果。命令证据保存命令、退出码和日志；人工/AI审阅保存步骤、来源和结论。
5. 实现或文件生成后仍未实际验证，保持`in_review`。没有工具时交付补丁，不能done。
6. 审阅者记录真实review_mode：independent/self_review/human/mixed。只有一个AI时可做明确标记的自审，不能编造第二位审查者。
7. 全部验收有证据，依赖也完成，才设done并引用证据文件；运行validate、render。填写交接记录。任务的evidence数组只引用本次有效通过记录；历史失败和旧记录保留在目录与交接中，不删除，也不作为当前通过证据。

状态变化不会修改课程事实。教师未回复、数据未获得、测试未执行、报告未提交等都需保持可见。材料ready与实际submitted有不同关卡。
代码/数据/契约变化使相关证据哈希失配时，审查影响范围并标`stale`；只重验受影响环节，不因普通文案修订重跑无关训练。

## 6. 阶段关卡

| 关卡 | 截止与含义 |
| --- | --- |
| `proposal-ready` | 2026-11-09：正式数据、预处理、技术与选题报告就绪 |
| `midterm-ready` | 2026-11-30：数仓、分析、模型、中期报告及答辩材料就绪 |
| `final-ready` | 2026-12-22前：系统、三AI、正式报告、PPT、复现与演练就绪 |
| `final-submitted` | 有实际三阶段提交及答辩凭证；不能从ready自动推定 |

建议12月13日内部功能冻结，12月14至18日复现演练，12月19至20日保留缓冲。若教师更新日期，保留真实来源并统一更新台账和相关计划。

各阶段材料按当期截止日交付，实际提交和答辩发生时立即保存回执。REL-07仅负责终期汇总核对，不是11月9日、11月30日提交或收集回执的前置条件。

## 7. 当前最关键的未决事项

- 数据时效：课程有2026年1月后与天池2025年6月后两处口径。需要能够证明满足较严格条款的真实数据，或教师对口径/历史数据例外的真实解释。经典数据集不能凭更新时间宣布合规。
- 真实成员、学号和分工尚未填写。
- 正式主数据、API服务与实际环境尚未冻结。
- 普通AI编码辅助不算业务系统完成AI模块；静态回放也不能替代真实LLM集成验收。
- 可选销量预测、关联规则、微调、生产强化、公开发表等默认不做。不能为加分牺牲核心交付或违规对外发布课程数据。

详细规则见AGENTS与ACCEPTANCE，逐项输出和验收条件见TASKS。凡称“完成”，应能指出对应任务和当前有效证据。
